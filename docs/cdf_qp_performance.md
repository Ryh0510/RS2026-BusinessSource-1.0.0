## 具体改动

1. 在单次 repair 中创建私有 `CdfQueryBatch`，默认按硬件能力使用至多四个独立的 FK/碰撞场景。批量距离、梯度、整条路径验证和各平滑窗口内的边验证并行执行；窗口之间仍按原顺序接受或拒绝。场景构建串行完成，工作结束前等待所有任务，资源不足时使用已建立的较少工作场景。
2. 缓存仅限当前不可变规划场景的这一次调用。键保留原始 double，不量化、不折回；距离键包含关节角/安全裕量/距离范围，运动键包含有向端点/检测步长。只缓存有效距离和已验证有效的边；两个缓存各最多 32768 项。缓存不跨项目、机器人、障碍物变化或下一次优化复用。
3. 最近特征的物体 ID 属于各自场景，不能跨工作场景共享。因此梯度仍由对应场景重新线性化，仅将距离观察值用于后续距离缓存。
4. 候选已不满足原来的距离接受条件时，不再进行对该候选无助于接受的整条运动扫描。保留原来两个条件的逻辑与关系、回溯次数及 alpha 序列。
5. 最终全路径验证绕过缓存，重新按原有 0.001 rad 步长进行碰撞查询；headless 随后再在另一场景独立回放验证。

本次命中 12072 次距离缓存、11521 次运动缓存。批量距离阶段累计约 74.1 秒，梯度约 8.1 秒，运动验证约 104.5 秒；这些数字只统计批量上下文，APF 内部串行查询等不在其中。

没有更改 QP 矩阵、权重、容差、轮数、APF 参数、平滑参数、关节符号、输出点数规则、时间戳规则或检测对象集合。使用更多独立场景会增加少量内存；工作数有上限，所有临时场景和缓存随 repair 销毁。

### 根因与改动

- Top-M 不考虑碰撞，低关节变化代价不保证容易避障。该候选原始连接中有 277 个碰撞段，密化后 4592 点。上一轮实现的批量 CDF 加速未覆盖 APF 内部有限差分及串行碰撞区间扫描。该难段反复切换势场和扩大锚点，单段约 12 分钟，尚未进入 QP；QP 一轮不会限制这些 APF 尝试。
- APF 每次有限差分的所有正负扰动同时交给独立场景查询，保持探针位置、梯度公式、正反向尝试顺序、14 个势场/每场最多 600 步、3 档锚点扩展和接收条件。单点距离与已通过的运动使用本次调用的精确缓存，失败查询不当成有效结果缓存。
- 碰撞区间收集、替换段验证和局部 QP 补救复用同一个批量上下文。仍按原顺序处理各区间，避免重叠窗口并发修改轨迹。批量任务采用动态领取，减少某些网格查询过慢导致其他工作场景空闲。
- 保留最终绕过缓存的全路径验收。未改关节符号、QP 数值设置、采样密度、轨迹时间、输出点数或脱困上限。单次标量直连检查等仍有串行部分，困难候选仍可能耗时较长。
- GUI 原入口在界面线程同步计算且未接 `progress`。现由 controller 在私有项目快照上运行工作线程，显示模态阶段窗口、累计时间、APF 势场/迭代和日志。工作线程完成后才释放窗口并通过原文档服务提交结果；期间文档变化时拒绝提交过期结果。
- 每次 GUI 优化写入 EXE 同目录的 `log/cdf/cdf_时间_进程号.log`，不能创建目录时回退用户应用数据目录。记录 EXE 完整路径、Release/Debug、输入来源与点数、有效参数、工作场景数、各阶段累计和相邻消息间耗时、诊断结果。结束摘要显示日志路径。阶段耗时不冒充完成百分比。
